## Section 3 of 25 — JupyterLab

A notebook is a file of ordered **cells**; the **kernel** is the separate Python process that actually executes code and remembers variables. A code cell runs when you execute it (Shift+Enter). A Markdown cell holds explanation, headings, and mathematical typesetting; a raw cell is unprocessed text. A saved notebook and a running kernel are different things. Saving records cell source and perhaps outputs, but it does not guarantee that a fresh kernel can reproduce them.

**Stateful execution** is the key mental model. Run a cell assigning x = 1, then a later cell printing x: the output is 1. Edit the first cell to x = 2 without running it, and the kernel still holds 1. Run the edited assignment and then print again: now it is 2. Out-of-order execution can conceal missing imports or stale values. “Restart Kernel and Run All Cells” is a useful reproducibility test because it clears in-memory definitions and executes source in order. A restart alone preserves the file and may preserve displayed outputs, but it clears the live Python variables.

### Scikit-learn: fit, transform, predict

Scikit-learn's common pattern is: construct an estimator, call fit on **training** data, and then call transform or predict on data. It includes familiar Module 290 algorithms (linear/logistic regression, trees, naive Bayes, SVMs, ensembles, K-means, PCA) plus preprocessing, splitting, cross-validation, and metrics. The consistency of the interface means we can exchange algorithms without redesigning the entire data pipeline.

**Feature scaling** matters because a distance or gradient can be dominated by a feature simply measured in larger units. StandardScaler performs z = (x − μ) / σ. Read this aloud: “z equals x minus mu, divided by sigma.” x is a value, μ (“mu”) is the training mean, and σ (“sigma”) is the training standard deviation. The complete meaning is “express this value as a number of training standard deviations away from the training mean.” If the mean is 10, the standard deviation is 2, and x is 14, then z is (14 − 10) / 2 = 2. MinMaxScaler instead maps training minimum and maximum to a chosen range, commonly zero through one. RobustScaler uses a median and interquartile range to be less sensitive to extremes; this is not a guarantee against intentionally poisoned data.

**Categorical encoding** converts labels such as protocol names into numeric features. One-hot encoding creates one indicator column per category, e.g. TCP → [1,0], UDP → [0,1]. The numbers are category membership, not a claim that UDP is “greater than” TCP. An arbitrary integer encoding can accidentally suggest such an order to some models. Missing-value imputers fill absent data with a learned statistic or neighbor-based estimate, but the fact that a value is missing may itself carry security meaning. Fit all scalers, encoders, and imputers on the *training fold only*; fitting them before the split leaks information from the held-out data into the model workflow.

train_test_split creates a held-out test set; cross_val_score repeats fitting/evaluation across training folds to reduce dependence on one split. An 80/20 split means 80% of rows are used for fitting and 20% for a final check, not that each class necessarily has that exact percentage unless the split is stratified. For security telemetry, random splitting may be overly optimistic if nearly identical events from one host or incident appear in both sets. A time-, host-, or campaign-aware split can better test the intended deployment setting. HTB introduces accuracy, mean squared error, precision, recall, and F1 here; class imbalance can make accuracy deceptively high. These are evaluation choices, not interchangeable scores.

HTB shows LogisticRegression(C=1.0). The C parameter is the **inverse** of regularization strength: smaller C generally means stronger penalization of large coefficients. After fit(X_train, y_train), predict(X_test) returns labels; a score or probability would use a different method. In the study notebook we keep a scaler and classifier in one scikit-learn Pipeline so fitting the pipeline on training rows also keeps its scaler training-only.

### PyTorch: tensors, graphs, and a training step

A tensor is a multidimensional numeric array. A flat three-number tensor has shape (3); four samples with two features each have shape (4, 2). PyTorch records operations on tensors requiring gradients in a dynamic computational graph during the forward pass; autograd uses that graph during backward() to calculate derivatives. GPU support is optional, not an assumption that every model should be moved to CUDA. This lesson's tiny demonstration runs on CPU to avoid needless GPU memory use.

HTB's example network maps 784 input features to 128 hidden units, applies ReLU, then maps 128 to 10 class scores. For a batch of 32 rows, its shapes are (32,784) → (32,128) → (32,10). ReLU replaces negative activations with zero. The page appends Softmax to make normalized class probabilities. **Important integration caveat:** PyTorch's CrossEntropyLoss expects raw class scores, called *logits*, and internally handles the log-softmax calculation. If using that loss, leave a final Softmax layer out of the training model; apply softmax only when probabilities are needed for interpretation. This is a technical correction to the illustrative page snippets, not a change to HTB's intended classifier concept.

An optimizer step follows θ_new = θ_old − η ∇_θ L. Read it “theta new equals theta old minus eta times the gradient of L with respect to theta.” θ (“theta”) is a parameter, η (“eta”) is the learning rate, ∇_θ L (“gradient of loss with respect to theta”) is a collection of loss slopes, and L is the loss. In plain English, move each parameter a small distance opposite the direction that would increase the error. If θ = 3, η = 0.1, and the gradient is 4, then θ_new = 3 − 0.1×4 = 2.6. In code, zero_grad() clears previous accumulated gradients, loss.backward() computes current ones, and optimizer.step() updates parameters. Without zero_grad(), multiple backward passes accumulate gradients, which can be intentional but is a common accidental bug.

For a batch of classification logits with shape (N, C), read N as “number of examples” and C as “number of classes.” torch.max(output, dim=1) provides both each row's largest *value* and its class *index*. The index is the predicted class, not the confidence probability. HTB's accuracy helper counts matching predicted and target labels and divides by N. Thus 3 correct predictions out of 4 give 3/4 = 0.75. Accuracy alone can hide rare-but-important malicious cases.

Dataset defines how to retrieve one row and its label; DataLoader gathers rows into shuffled or ordered batches. Training mode and evaluation mode matter for layers such as dropout and batch normalization. state_dict holds model parameters for saving/loading. Only load model files from trusted sources: generic PyTorch object deserialization may execute attacker-controlled code, and the page's simple torch.load example is not a safe recipe for untrusted downloads. The study notebook neither downloads nor loads a model file.

## Section 5 of 25 — Datasets

A **dataset** is a collection of examples. The representation depends on the problem: table rows for network events, pixel arrays for images, sequences of tokens for text, or time-ordered measurements for a time series. A *feature* is information supplied to a model; a *label* is the answer we want a supervised model to learn. The same raw field can be a useful feature, a misleading shortcut, or an inappropriate identifier depending on the deployment question. This section is about inspecting the provided data, **not yet cleaning or training on it**.

HTB names seven desirable dataset properties: relevance, completeness, consistency, quality, representativeness, balance, and sufficient size. They are separate checks. A huge dataset can still have wrong labels; a perfectly complete dataset can still omit the attacks seen in deployment. In cybersecurity, an evaluation set dominated by routine traffic can make an always-normal detector appear accurate while it misses every malicious event. Artificially balancing classes during training may help learning, but the final test should also reflect a realistic deployment prevalence when estimating alert workload.

The course's **demo network-log CSV** has one row per event and these columns: log_id (identifier), source_ip (origin address), destination_port (service endpoint number), protocol (HTB's broad service/protocol category), bytes_transferred (volume), and threat_level (course label: 0 normal, 1 low threat, 2 high threat). A port such as 22 is often associated with SSH, but a port alone does not prove what actually ran or whether the event was malicious. An IP address may identify a host but can also make a model memorize lab-specific addresses; log_id is especially likely to be an identifier rather than a causal signal. We should decide feature suitability only after understanding the task and split.

The linked file is a small ZIP containing demo_dataset.csv. The [dataset inspection notebook](Dataset_Inspection_Study.ipynb) accepts a local ZIP (or a local path provided through an environment variable) and otherwise downloads the same HTB course archive. It checks the expected member and a size bound before parsing the CSV in memory. This is a teaching convenience; HTB's page assumes the CSV has already been downloaded and extracted. No downloaded archive, network IP, or data output is committed to the repository.

Read the last expression as “is-null, then sum”: pandas converts each null check to True or False and sums the True values. For example, [False, True, True, False] sums to 2 missing values. info() already prints its report, so wrapping it in print() also prints its return value, None; the notebook calls it directly.

**Preprocessing** is the bridge between raw records and model-ready features. The validators are domain rules, not statistical estimates. For a port p, 0 ≤ p ≤ 65535 is read “zero is less than or equal to p, and p is less than or equal to sixty-five thousand five hundred thirty-five.” p means one candidate port. A value of 443 passes and 70,000 fails. For bytes b, b ≥ 0 is read “b is greater than or equal to zero”; negative transfer volume is invalid. HTB permits threat labels 0, 1, and 2. Unknown markers such as “?” and −1 are not a fourth threat class. Its protocol allowlist includes TCP, TLS, SSH, POP3, DNS, HTTPS, SMTP, FTP, UDP, and HTTP; this mixes transport and application/service names but reflects the course's column semantics.

A regex can still miss semantic nuances such as leading-zero representations, so a production validator should use an IP-address parser and an explicit IPv4/IPv6 policy. When applying any validator to this CSV, handle actual nulls before string matching; casting a null to text produces the word “nan,” which must not be accepted as an address.

**Dropping** removes every row with at least one failed rule. A single row can fail several checks, so adding per-column invalid counts would double-count overlaps. **Imputation** replaces an unknown value using a rule learned from observed values. NaN means “not a number” and is pandas/NumPy's common missing marker. The median is the middle sorted numeric value; for 100, 200, and 9,000 it is 200, which is less pulled by the outlier than the mean. The mode is the most frequent category; three TCP rows and two UDP rows give TCP. SimpleImputer learns such a statistic with fit and inserts it with transform. KNNImputer instead borrows information from similar rows: KNN is read “k nearest neighbors,” where k is the number of nearby rows consulted. For an intuitive two-feature example, (2,2) is closer to (3,2) than to (10,10). Neighbor distances depend on feature scale and missingness, so KNN is not automatically more truthful.

**One-hot encoding** makes one binary indicator per observed protocol category. For TCP and UDP, TCP → [1, 0] and UDP → [0, 1]. The 1 means membership, not a numeric ranking. `OneHotEncoder(handle_unknown='ignore')` can transform a later unseen category without crashing; that category gets zero in all learned indicator columns, which should be monitored rather than mistaken for a known category. Complete meaning: preserve ordering while shrinking large gaps. For b=0, z=0; for b=9, z≈2.30; for b=999, z≈6.91. `np.log1p` computes this accurately even for small values. ## Section 8 of 25 — Metrics for Evaluating a Model

This section introduces no new Python example. Its purpose is to interpret model results *after* training, not to train or tune on the held-out test set. Choose the **positive class** first. In a binary threat detector, call “threat” positive and “benign” negative. **TP** (true positive) is a threat correctly alerted; **FP** (false positive) is benign traffic incorrectly alerted; **FN** (false negative) is a threat missed; **TN** (true negative) is benign traffic correctly left alone. These are four cells of a **confusion matrix**, not four different models. “True/false” describes correctness, while “positive/negative” describes the predicted alert side.

**Accuracy** = (TP + TN) / (TP + FP + FN + TN). Read it “true positives plus true negatives, divided by all cases.” The numerator counts correct decisions; the denominator counts every decision. In plain English, it is the fraction classified correctly. A classifier saying “benign” for all 100 events when 99 are benign earns 99/100 = 99% accuracy but catches zero of the one threat. The large-looking number hides the failure that matters.

**Precision** = TP / (TP + FP). Read it “true positives divided by true positives plus false positives.” The denominator is *everything the model alerted on*. In plain English, among alerts, what fraction is real? If 8 of 10 alerts are true threats, TP=8 and FP=2, so precision=8/10=0.8. False alarms consume analyst time and can cause users to ignore alerts, so precision is operationally important. If no positive predictions exist, the denominator is zero and a reporting convention must be chosen; do not silently claim perfect precision.

**Recall** = TP / (TP + FN). Read it “true positives divided by true positives plus false negatives.” The denominator is *all actual threats*. In plain English, of the attacks that really happened, what fraction did we catch? If the 8 correctly alerted threats came from 20 real threats, FN=12 and recall=8/20=0.4. High recall reduces misses but can come with many false alarms. If a test set contains no positives, recall has a zero denominator and needs an explicit reporting convention.

**F1** = 2 × (precision × recall) / (precision + recall). Read it “F one equals two times precision times recall, divided by precision plus recall.” Each term is a rate from above; the complete expression is their **harmonic mean**, which drops sharply when either is weak. For precision 0.8 and recall 0.4, F1 = 2×0.8×0.4/(0.8+0.4) ≈ 0.533. It is not their ordinary average (0.6), does not include true negatives, and does not itself encode the business cost of an FP versus an FN.

For one concrete 100-event confusion matrix, let TP=8, FP=2, FN=12, TN=78. Read these aloud as “eight detected threats, two false alerts, twelve missed threats, seventy-eight correctly quiet benign events.” Accuracy=(8+78)/100=0.86; precision=8/(8+2)=0.80; recall=8/(8+12)=0.40; F1≈0.533. The same model looks respectable by accuracy and weak by recall. This is why the HTB page asks us to consider class imbalance, segment-by-segment behavior, and the cost of misses and false alarms rather than quoting one number.

HTB also names **specificity** = TN/(TN+FP), read “true negatives divided by all actual negatives,” which measures correct rejection of benign events. **ROC AUC** is “receiver operating characteristic area under the curve”; it summarizes discrimination across score thresholds, not the alert quality at one operating threshold. **MCC** is the Matthews correlation coefficient, a summary using all four confusion-matrix cells that can be useful with imbalance. A confusion matrix exposes the raw counts from which many metrics arise. These are additional evaluation lenses, not automatic replacements for precision and recall. For the course's three-class threat labels (0/1/2), TP/FP/FN/TN must be defined *per class* (one-versus-rest), or a micro/macro/weighted averaging rule must be stated before a single precision, recall, or F1 number is meaningful. A macro average gives each class equal weight; a weighted average reflects class support. This multiclass clarification is beyond the page's binary spam illustration but necessary before evaluating the course dataset.

## Section 9 of 25 — Spam Classification

Spam is unsolicited bulk messaging; besides inconvenience it can carry phishing links or malware. A **classifier** assigns a label such as spam/not-spam. HTB uses **Naive Bayes** to illustrate how observing email features changes an initial belief. The [worked-example notebook](Spam_Classification_Bayes_Study.ipynb) calculates the page's exact numbers; it is arithmetic on supplied probabilities, **not a trained email filter** and not evidence about real messages.

Bayes' theorem is **P(A | B) = P(B | A) × P(A) / P(B)**. Read `P` as “probability,” `|` as “given,” and the full left side as “the probability of A given B.” `P(A)` is the **prior** belief about A before seeing B. `P(B | A)` is the **likelihood** of seeing B when A is true. `P(B)` is the overall or **marginal** probability of seeing B. `P(A | B)` is the updated **posterior** belief. Whole equation in plain English: multiply the prior by how well the observation fits A, then divide by how common that observation is overall. The denominator normalizes the answer so the posteriors across mutually exclusive classes sum to one. Crucially, **P(spam | features)** is not the same as **P(features | spam)**: reversing the condition answers a different question.

For the lesson, A is “Spam” and B is the pair of observed features F₁ and F₂. Read **F₁** as “F sub one,” and **P(F₁,F₂ | Spam)** as “the probability of F sub one and F sub two given spam.” The *naive conditional-independence assumption* writes **P(F₁,F₂ | Spam) ≈ P(F₁ | Spam) × P(F₂ | Spam)**. Read the approximation sign as “is approximately.” Each feature probability describes the feature within the spam class, and multiplying treats the features as independent once the class is fixed. HTB writes an equals sign for this model assumption; real email terms can be correlated, so the equality is not a general law. The same factorization is made separately for not-spam. A word like “free” may correlate with “prize”; counting them as independent may overstate the evidence.

HTB supplies the prior probabilities P(Spam)=0.3 and P(Not Spam)=0.7. Under spam, the two feature likelihoods are 0.4 and 0.5, giving 0.4×0.5=0.20. Under not-spam, they are 0.2 and 0.3, giving 0.2×0.3=0.06. **The law of total probability** combines both ways the features can occur: **P(F₁,F₂) = P(F₁,F₂ | Spam)P(Spam) + P(F₁,F₂ | Not Spam)P(Not Spam)**. Read that as “the probability of both features equals the spam-path probability plus the not-spam-path probability.” Numerically, 0.20×0.30 + 0.06×0.70 = 0.060 + 0.042 = 0.102.

The spam posterior is **0.060 / 0.102 ≈ 0.588** (read “approximately fifty-eight point eight percent”), and the not-spam posterior is **0.042 / 0.102 ≈ 0.412**. They sum to one, and 0.588 > 0.412, so HTB's higher-posterior rule predicts spam. An **unnormalized score** such as 0.060 can be compared against 0.042 to choose a class, but it is *not* itself the final 60% spam probability. In a deployed filter, the decision threshold and class prior should reflect actual mail prevalence and the cost of false positives and missed phishing; that operational tuning is not performed in this section. Real implementations also estimate feature probabilities from training mail, smooth unseen features, and usually sum log-probabilities to avoid multiplying many tiny numbers into floating-point underflow. Those are production considerations, not extra steps claimed for HTB's hand calculation.

## Section 11 of 25 — Preprocessing the Spam Dataset

The [SMS preprocessing notebook](SMS_Spam_Preprocessing_Study.ipynb) starts with the same official ZIP and exact-deduplicated rows, then shows HTB's stages *in order*: lowercase → remove selected characters → tokenize → remove stop words → stem → join tokens. Keeping a named DataFrame for each stage makes the changes inspectable and preserves the original messages for comparison. HTB overwrites one `df['message']` column repeatedly, which is concise but makes it easier to lose track of what was removed. This notebook does **not** vectorize text, split the corpus, or fit a classifier yet.

**Lowercasing** maps `FREE` and `free` to the same string, reducing unnecessary vocabulary variants. A **regular expression** (regex) then removes every character outside lowercase ASCII letters (`a-z`), whitespace (`\s`), `$`, and `!`. Read `[^a-z\s$!]` as “any character *not* in this allowed set”; the caret inside the square brackets means *not*, unlike a caret at the start of an entire regex, which means the beginning of a string. HTB intentionally retains `$` and `!` as possible spam signals. It also removes digits, URLs' punctuation, and non-ASCII letters, which can discard valuable evidence in modern phishing. This is the course's teaching choice, not a universal best practice.

**Tokenization** changes one string into a list of smaller units. `word_tokenize('free prize!')` gives units such as `['free', 'prize', '!']`; a token is not necessarily a natural-language word. NLTK's `punkt` and `punkt_tab` resources support its sentence/word tokenization; the `stopwords` resource supplies common English words. The notebook checks for these installed resources and downloads a missing one only when run in a machine that needs it. They are already available in the user's `AI` environment, so our validation did not make another download.

**Stop-word removal** filters tokens in NLTK's English stop-word set, such as “the” or “and.” This can shrink the vocabulary but also erase meaningful context: “not” can reverse a claim, and losing it may invert the apparent meaning of a message. A set is used for fast membership checks. **Stemming** applies PorterStemmer to fold related word forms into a common stem; `running` can become `run`, but stems are algorithmic fragments, not guaranteed dictionary base words. Stemming reduces separate feature columns but can collapse distinctions or produce odd-looking tokens. **Joining** with `' '.join(tokens)` returns a space-separated string that a later vectorizer can accept. Joining does not recover removed punctuation, numbers, stop words, or original capitalization.

Preprocessing should be defined identically for training and inference; a classifier trained on lowercase/stemmed text but served raw text would see a different feature representation. The page says these operations improve performance, but that is a hypothesis to test on held-out data, not a guarantee. The notebook validates row counts, label preservation, token-list/string types, deterministic examples, and finite stage outputs while making no claims about model accuracy yet.

## Section 12 of 25 — Feature Extraction

The Section 11 [SMS notebook](SMS_Spam_Preprocessing_Study.ipynb) now appends Section 12 cells **after** its preprocessing recap. A machine-learning classifier needs numbers, not raw message strings. A **bag-of-words** representation learns a vocabulary of terms and stores a count for each term in each message. A *unigram* is one term; a *bigram* is two neighboring terms. For `free prize free`, columns `[free, prize, free prize]` have counts `[2, 1, 1]`. Unigrams lose word order; adding bigrams captures only local two-term order, not sentence structure or meaning.

Write a count-matrix entry as **Xᵢⱼ** or `X[i,j]`, read “X sub i comma j.” `i` identifies a message, `j` identifies a vocabulary term, and the value counts that term in that message. The complete matrix **X** has shape `(N,V)`, read “N by V,” where N is the number of messages and V the number of learned vocabulary terms. The label vector **y** has N entries; `y[i]` (say “y sub i”) is 1 for spam and 0 for ham in the corresponding row. These are labels, not predicted probabilities. We verify that the row order is preserved so feature row `i` still matches answer `y[i]`.

HTB uses `CountVectorizer(min_df=1, max_df=0.9, ngram_range=(1,2))`. `df` here means **document frequency**: how many distinct messages contain a term, regardless of how often the term repeats within one message. `min_df=1` keeps terms seen in at least one message. `max_df=0.9` rejects a term seen in more than 90% of messages; for five messages, a term present in all five has frequency 5/5=1.0, read “five divided by five equals one,” and is excluded because 1.0>0.9. `ngram_range=(1,2)` includes individual terms and adjacent pairs. A bigram has its own document frequency independent of either unigram's frequency.

HTB's hand-drawn unigram table includes the one-character term `a`, but the shown `CountVectorizer` code uses scikit-learn's default token pattern, which drops single-character tokens. The notebook tests the actual five-document vocabulary: `a` is absent, `the` is absent because it appears in all five, while terms such as `free`, `prize`, and `free prize` can be inspected directly. Treat the course table as a conceptual illustration, not an exact dump of those defaults.

There is also a cross-section mismatch: Section 11 preserves `$` and `!` as possible spam cues, but this Section 12 `CountVectorizer` uses the same default word-token pattern, which ignores standalone punctuation. Keeping symbols in the intermediate string does **not** make them columns in `X`. A custom tokenizer or explicit symbol features would be needed to use them in a real detector; HTB does not introduce that customization here.

The real SMS corpus produces a **sparse** count matrix: most messages do not contain most vocabulary terms, so storing all zero cells densely would waste memory. `X.nnz` counts stored nonzero entries; it is not the number of messages or vocabulary terms. The notebook only densifies three selected columns of a *five-row toy example*, never the full corpus. It fits the vectorizer to the entire preprocessed corpus because that is HTB's Section 12 illustration, but this exposes vocabulary learned from future held-out rows. Before evaluating a trained model, split rows first, fit the vectorizer on **training** messages only, and transform validation/test messages with the learned vocabulary. That correction belongs to a later model/evaluation section; no classifier or TF-IDF weighting is implemented here.

Validation in the user's `AI` environment on the current UCI archive: 5,171 deduplicated/preprocessed messages became a sparse **5,171 × 37,065** matrix with **80,177** nonzero count cells; labels remained 4,518 ham (0) and 653 spam (1). These numbers describe this exact corpus and preprocessing configuration, not a stable API contract or accuracy claim.

## Section 13 of 25 — Training and Evaluation (Spam Detection)

HTB introduces **Multinomial Naive Bayes** for nonnegative text-count features and a scikit-learn **Pipeline** combining `CountVectorizer` with `MultinomialNB`. A pipeline is a data-processing chain: message string → vectorizer learned word-count columns → classifier class scores/predictions. It helps apply identical vectorization at training and prediction time. The [continuing SMS notebook](SMS_Spam_Preprocessing_Study.ipynb) appends this section after Section 12's recap; prior cells remain unchanged.

The classifier's **alpha** (α, say “alpha”) is an additive smoothing parameter. A simplified token likelihood is **P(w | c) ≈ (N₍w,c₎ + α) / (N₍c₎ + αV)**. Read it “probability of word w given class c is approximately count of w in c plus alpha, divided by total token count in c plus alpha times vocabulary size.” `w` is one word, `c` one class, `N₍w,c₎` its within-class token count, `N₍c₎` all token counts in that class, and `V` the vocabulary size. Complete meaning: give each vocabulary term a small starting count so an unseen word does not receive zero probability. If a term appears twice among 10 class tokens, V=5, and α=1, then (2+1)/(10+1×5)=3/15=0.20; a never-seen term gets 1/15 rather than zero. HTB searches α in `[0.01, 0.1, 0.15, 0.2, 0.25, 0.5, 0.75, 1.0]`.

**Five-fold cross-validation** divides the tuning data into five parts: train on four, score on the fifth, rotate, then average. HTB uses `GridSearchCV(cv=5, scoring='f1')` to compare eight alpha values. That means up to 8×5=40 fold fits plus a refit of the selected model. `F1` is the harmonic mean of precision and recall explained in Section 8; with high precision but low recall it stays modest. The notebook uses one worker (`n_jobs=1`) and sparse matrices to control memory. Its `Pipeline` starts with a *fresh* vectorizer; the Section 12 whole-corpus vectorizer is not reused in this evaluation.

The course calls `grid_search.fit(df['message'], y)` on the **full dataset**, then shows a confusion-matrix graphic and five handpicked messages. Without a separately reserved test set, the page's workflow does not demonstrate an unbiased final performance estimate. The notebook reserves 20% of rows first, stratifying to keep roughly the same ham/spam balance, runs the alpha search on the other 80%, and evaluates the best pipeline on the untouched 20% **once**. In `confusion_matrix(..., labels=[0,1])`, read the four cells `[[TN,FP],[FN,TP]]` as “true negatives, false positives, false negatives, true positives,” where positive means spam. The displayed counts are then accompanied by precision, recall, and F1. Even that random row split can be optimistic if near-duplicate messages or campaigns occur on both sides; a time/campaign-aware split is a production alternative, not an extra HTB step.

The five page examples are useful *demonstrations*: `preprocess_message` repeats the Section 11 rules, then `best_model.predict` and `predict_proba` apply the fitted vectorizer/classifier together. `predict_proba` produces one model probability estimate per class; its columns follow `best_model.classes_`, so find class 1 by label. The page's example output is not promised as the notebook's exact output.

## Section 15 of 25 — Network Anomaly Detection

An **anomaly** is an observation unusually far from a learned baseline; an **intrusion** is an unauthorized or malicious action. An odd network connection is a lead for investigation, not proof of intrusion. A KDD row is a summarized connection record with features such as duration, protocol, service, connection status, byte counts, and rates; it is not an individual packet. HTB introduces a **random forest**, an ensemble (group) of decision trees. A tree asks successive feature questions, such as “is `duration` greater than a threshold?” A classification forest gives each tree a vote and chooses the most common class; if three trees say normal, attack, attack, the forest predicts attack. For regression, it averages numeric outputs instead.

**Bootstrapping** draws training rows *with replacement*: from rows A, B, C, D, one four-draw sample could be A, C, C, D. C appears twice and B is absent. Different trees also consider random subsets of features at each split. Both randomness sources make trees less alike, so one tree's quirks have less sway over the vote. One way to write the classification rule is **ŷ = mode(T₁(x), …, Tᴮ(x))**. Say “y hat equals the mode—the most frequent value—of tree one at x through tree B at x.” `x` is one connection's feature row, `Tᵦ(x)` (say “tree sub b of x”) is tree b's predicted class, `B` is the number of trees, and `ŷ` (“y hat”) is the forest's final predicted label. This is a compact description of voting, not a promise that the model is always correct.

The page says a forest can be trained **exclusively on normal traffic** and flag low-confidence departures. That wording needs care: a standard `RandomForestClassifier` given only one class cannot learn a normal-versus-attack boundary; it will only know “normal.” A supervised forest trained on labeled normal *and* attack rows is **intrusion classification**, while genuinely normal-only anomaly detection requires a separately specified scoring/threshold method or different algorithm. We will not silently claim that one is the other. HTB's modified NSL-KDD file provides an `attack` field containing `normal` or an attack type. The final `level` field is a difficulty/metadata value, not another attack category. A binary target can be derived in a later section if HTB does so; this section only loads and inspects the data.

The [new network-anomaly notebook](Network_Anomaly_Detection_Study.ipynb) names all 43 columns exactly as the page lists them and reads the HTB-provided `KDD+.txt` member directly from the ZIP. This avoids the page's broad `extractall('.')` call, which could overwrite files if a downloaded archive ever contained unexpected paths. The notebook checks the archive member, row/column counts, missing labels, sample rows, and leading attack labels without fitting any model. The ZIP was downloaded from the URL printed on the authenticated HTB page to the user's Downloads folder; it is not committed.
