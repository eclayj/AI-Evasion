## Section 1 of 25 — Introduction

Module 290 established the main learning paradigms and algorithms. This module turns those ideas into a **data-to-model workflow**: inspect and understand a dataset, prepare its features and labels, train a model, then evaluate it on data not used to fit it. That last distinction matters: a model that memorizes training examples is not necessarily useful on new traffic or messages. HTB introduces three application tracks, each with a different input representation and security question:

1. **SMS spam classification:** Given message text, predict spam versus non-spam. The unit of analysis is a message, and the output is a class label or score. A keyword alone may be insufficient; ambiguous wording and adversarial paraphrases matter.
2. **Network anomaly detection:** Given traffic-derived features, identify abnormal or potentially malicious behavior. **Anomalous does not automatically mean malicious**—a legitimate deployment or maintenance event can be unusual. Label quality, base rates, and false alarms matter.
3. **Malware classification from byteplots:** Convert binary bytes into an image-like grid and train a visual classifier. A byteplot is a *representation of a binary*, not proof that a program is safe or unsafe. Changes to packing, padding, or file structure can change the image without changing the underlying behavior.

## Section 3 of 25 — JupyterLab

A notebook is a file of ordered **cells**; the **kernel** is the separate Python process that actually executes code and remembers variables. A code cell runs when you execute it (Shift+Enter). A Markdown cell holds explanation, headings, and mathematical typesetting; a raw cell is unprocessed text. A saved notebook and a running kernel are different things. Saving records cell source and perhaps outputs, but it does not guarantee that a fresh kernel can reproduce them.

**Stateful execution** is the key mental model. Run a cell assigning x = 1, then a later cell printing x: the output is 1. Edit the first cell to x = 2 without running it, and the kernel still holds 1. Run the edited assignment and then print again: now it is 2. Out-of-order execution can conceal missing imports or stale values. “Restart Kernel and Run All Cells” is a useful reproducibility test because it clears in-memory definitions and executes source in order. A restart alone preserves the file and may preserve displayed outputs, but it clears the live Python variables.

HTB's illustrative DataFrame creates two columns of 50 independent random numbers and plots them as a scatter plot. NumPy's random.rand(50) returns 50 samples from the interval [0, 1), read “from zero inclusive to one exclusive.” Multiplying the second set by 10 scales that column to [0, 10): a draw of 0.37 becomes 3.7. A pandas DataFrame is a labeled table; head() displays the first five rows. The plot is a visualization of synthetic data, **not evidence of a model relationship**. In the accompanying [JupyterLab study notebook](JupyterLab_Study.ipynb), a fixed random seed is a labeled teaching addition so the same demonstration can be checked repeatedly.

The local AI environment already provides JupyterLab; no installation or running server is necessary for this lesson. ### Scikit-learn: fit, transform, predict

Scikit-learn's common pattern is: construct an estimator, call fit on **training** data, and then call transform or predict on data. It includes familiar Module 290 algorithms (linear/logistic regression, trees, naive Bayes, SVMs, ensembles, K-means, PCA) plus preprocessing, splitting, cross-validation, and metrics. The consistency of the interface means we can exchange algorithms without redesigning the entire data pipeline.

**Feature scaling** matters because a distance or gradient can be dominated by a feature simply measured in larger units. StandardScaler performs z = (x − μ) / σ. Read this aloud: “z equals x minus mu, divided by sigma.” x is a value, μ (“mu”) is the training mean, and σ (“sigma”) is the training standard deviation. The complete meaning is “express this value as a number of training standard deviations away from the training mean.” If the mean is 10, the standard deviation is 2, and x is 14, then z is (14 − 10) / 2 = 2. MinMaxScaler instead maps training minimum and maximum to a chosen range, commonly zero through one. RobustScaler uses a median and interquartile range to be less sensitive to extremes; this is not a guarantee against intentionally poisoned data.

**Categorical encoding** converts labels such as protocol names into numeric features. One-hot encoding creates one indicator column per category, e.g. TCP → [1,0], UDP → [0,1]. The numbers are category membership, not a claim that UDP is “greater than” TCP. An arbitrary integer encoding can accidentally suggest such an order to some models. Missing-value imputers fill absent data with a learned statistic or neighbor-based estimate, but the fact that a value is missing may itself carry security meaning. Fit all scalers, encoders, and imputers on the *training fold only*; fitting them before the split leaks information from the held-out data into the model workflow.

train_test_split creates a held-out test set; cross_val_score repeats fitting/evaluation across training folds to reduce dependence on one split. An 80/20 split means 80% of rows are used for fitting and 20% for a final check, not that each class necessarily has that exact percentage unless the split is stratified. For security telemetry, random splitting may be overly optimistic if nearly identical events from one host or incident appear in both sets. A time-, host-, or campaign-aware split can better test the intended deployment setting. HTB introduces accuracy, mean squared error, precision, recall, and F1 here; class imbalance can make accuracy deceptively high. These are evaluation choices, not interchangeable scores.

HTB shows LogisticRegression(C=1.0). The C parameter is the **inverse** of regularization strength: smaller C generally means stronger penalization of large coefficients. After fit(X_train, y_train), predict(X_test) returns labels; a score or probability would use a different method. In the study notebook we keep a scaler and classifier in one scikit-learn Pipeline so fitting the pipeline on training rows also keeps its scaler training-only.

### PyTorch: tensors, graphs, and a training step

A tensor is a multidimensional numeric array. A flat three-number tensor has shape (3); four samples with two features each have shape (4, 2). PyTorch records operations on tensors requiring gradients in a dynamic computational graph during the forward pass; autograd uses that graph during backward() to calculate derivatives. GPU support is optional, not an assumption that every model should be moved to CUDA. This lesson's tiny demonstration runs on CPU to avoid needless GPU memory use.

HTB's example network maps 784 input features to 128 hidden units, applies ReLU, then maps 128 to 10 class scores. For a batch of 32 rows, its shapes are (32,784) → (32,128) → (32,10). ReLU replaces negative activations with zero. The page appends Softmax to make normalized class probabilities. **Important integration caveat:** PyTorch's CrossEntropyLoss expects raw class scores, called *logits*, and internally handles the log-softmax calculation. If using that loss, leave a final Softmax layer out of the training model; apply softmax only when probabilities are needed for interpretation. This is a technical correction to the illustrative page snippets, not a change to HTB's intended classifier concept.

An optimizer step follows θ_new = θ_old − η ∇_θ L. Read it “theta new equals theta old minus eta times the gradient of L with respect to theta.” θ (“theta”) is a parameter, η (“eta”) is the learning rate, ∇_θ L (“gradient of loss with respect to theta”) is a collection of loss slopes, and L is the loss. In plain English, move each parameter a small distance opposite the direction that would increase the error. If θ = 3, η = 0.1, and the gradient is 4, then θ_new = 3 − 0.1×4 = 2.6. In code, zero_grad() clears previous accumulated gradients, loss.backward() computes current ones, and optimizer.step() updates parameters. Without zero_grad(), multiple backward passes accumulate gradients, which can be intentional but is a common accidental bug.

For a batch of classification logits with shape (N, C), read N as “number of examples” and C as “number of classes.” torch.max(output, dim=1) provides both each row's largest *value* and its class *index*. The index is the predicted class, not the confidence probability. HTB's accuracy helper counts matching predicted and target labels and divides by N. Thus 3 correct predictions out of 4 give 3/4 = 0.75. Accuracy alone can hide rare-but-important malicious cases.

Dataset defines how to retrieve one row and its label; DataLoader gathers rows into shuffled or ordered batches. Training mode and evaluation mode matter for layers such as dropout and batch normalization. state_dict holds model parameters for saving/loading. Only load model files from trusted sources: generic PyTorch object deserialization may execute attacker-controlled code, and the page's simple torch.load example is not a safe recipe for untrusted downloads. The study notebook neither downloads nor loads a model file.

## Section 5 of 25 — Datasets

A **dataset** is a collection of examples. The representation depends on the problem: table rows for network events, pixel arrays for images, sequences of tokens for text, or time-ordered measurements for a time series. A *feature* is information supplied to a model; a *label* is the answer we want a supervised model to learn. The same raw field can be a useful feature, a misleading shortcut, or an inappropriate identifier depending on the deployment question. This section is about inspecting the provided data, **not yet cleaning or training on it**.

HTB names seven desirable dataset properties: relevance, completeness, consistency, quality, representativeness, balance, and sufficient size. They are separate checks. A huge dataset can still have wrong labels; a perfectly complete dataset can still omit the attacks seen in deployment. In cybersecurity, an evaluation set dominated by routine traffic can make an always-normal detector appear accurate while it misses every malicious event. Artificially balancing classes during training may help learning, but the final test should also reflect a realistic deployment prevalence when estimating alert workload.

The course's **demo network-log CSV** has one row per event and these columns: log_id (identifier), source_ip (origin address), destination_port (service endpoint number), protocol (HTB's broad service/protocol category), bytes_transferred (volume), and threat_level (course label: 0 normal, 1 low threat, 2 high threat). A port such as 22 is often associated with SSH, but a port alone does not prove what actually ran or whether the event was malicious. An IP address may identify a host but can also make a model memorize lab-specific addresses; log_id is especially likely to be an identifier rather than a causal signal. We should decide feature suitability only after understanding the task and split.

The linked file is a small ZIP containing demo_dataset.csv. The [dataset inspection notebook](Dataset_Inspection_Study.ipynb) accepts a local ZIP (or a local path provided through an environment variable) and otherwise downloads the same HTB course archive. It checks the expected member and a size bound before parsing the CSV in memory. This is a teaching convenience; HTB's page assumes the CSV has already been downloaded and extracted. No downloaded archive, network IP, or data output is committed to the repository.

HTB's first inspection calls have distinct jobs: data.head() previews the first five records; data.info() prints each column's type and non-null count; data.isnull().sum() counts actual nulls per column. Read the last expression as “is-null, then sum”: pandas converts each null check to True or False and sums the True values. For example, [False, True, True, False] sums to 2 missing values. info() already prints its report, so wrapping it in print() also prints its return value, None; the notebook calls it directly.

The page warns that ostensibly numeric fields can contain text and that threat_level may include “?” or −1. These are **sentinel or invalid values**, not necessarily pandas nulls. In the downloaded sample, rows include STRING_PORT in destination_port, NEGATIVE and NON_NUMERIC in bytes_transferred, and “?” in threat_level. Therefore a null count of zero would *not* mean the data is clean. The notebook reports raw label frequencies and counts values that fail a numeric check without altering any row. Converting, dropping, or imputing those values belongs to later preprocessing sections; silently doing so here would hide the problem we are meant to notice.

Read-only result from the downloaded course ZIP in the AI environment: **100 rows and 6 columns**; one actual null in source_ip and one in destination_port; six non-null but non-numeric destination ports; three non-null but non-numeric byte counts; and four “?” threat labels. The raw label counts are 34 zeros, 35 ones, 27 twos, and 4 question marks. This illustrates the distinction above: threat_level reports **zero pandas nulls** even though four labels are unknown. The page mentions −1 as another possible unknown value, but it was not observed in this downloaded sample.

Data quality also has an adversarial dimension: a malformed log field can be accidental corruption or an attacker-controlled string. Parsing and schema checks should happen before model code trusts the field. For a realistic detector, consider source provenance, duplicate events, time ordering, label-generation rules, and whether the same host or incident leaks across training and test sets. Those are security and production cautions, not extra HTB steps in this introductory dataset inspection.

## Section 6 of 25 — Data Preprocessing

**Preprocessing** is the bridge between raw records and model-ready features. HTB distinguishes cleaning (missing/invalid entries and duplicates), transformation (scaling/encoding/reduction), integration (combining sources), and formatting (types/shapes). This section concentrates on identifying invalid values and two responses: drop affected rows or impute values. The later **Data Transformation** section should not be pre-implemented here. The [preprocessing study notebook](Data_Preprocessing_Study.ipynb) starts from the Section 5 CSV, keeps the original DataFrame unchanged, and gives each response a separate named branch.

The validators are domain rules, not statistical estimates. For a port p, 0 ≤ p ≤ 65535 is read “zero is less than or equal to p, and p is less than or equal to sixty-five thousand five hundred thirty-five.” p means one candidate port. A value of 443 passes and 70,000 fails. For bytes b, b ≥ 0 is read “b is greater than or equal to zero”; negative transfer volume is invalid. HTB permits threat labels 0, 1, and 2. Unknown markers such as “?” and −1 are not a fourth threat class. Its protocol allowlist includes TCP, TLS, SSH, POP3, DNS, HTTPS, SMTP, FTP, UDP, and HTTP; this mixes transport and application/service names but reflects the course's column semantics.

HTB demonstrates an IPv4 regular expression. Its anchors ^ and $ mean “beginning” and “end” so extra characters are rejected; the escaped dot means a literal period, and the groups constrain each octet to 0–255. A regex can still miss semantic nuances such as leading-zero representations, so a production validator should use an IP-address parser and an explicit IPv4/IPv6 policy. When applying any validator to this CSV, handle actual nulls before string matching; casting a null to text produces the word “nan,” which must not be accepted as an address.

**Dropping** removes every row with at least one failed rule. A single row can fail several checks, so adding per-column invalid counts would double-count overlaps. HTB's successive drop(..., errors='ignore') calls avoid an error when overlapping indexes have already been removed. The course says this leaves **77 clean rows** from 100. The notebook reports the union of invalid row indexes and verifies the resulting count against the downloaded sample. This is a deliberate quality-versus-coverage tradeoff: if bad fields correlate with attacks, dropping them can bias the remaining data.

Validation against the downloaded 100-row sample found 15 invalid source IPs, 8 invalid ports, 2 invalid protocols, 3 invalid byte counts, and 4 invalid threat labels. Those add to 32 failures, but only **23 distinct rows** fail at least one rule; some rows fail more than one. Thus 100 − 23 = **77**, read “one hundred minus twenty-three equals seventy-seven,” rows remain, matching HTB. The drop branch still holds some numeric-looking columns as text because filtering rows does not itself convert pandas dtypes; that belongs to a later transformation decision.

**Imputation** replaces an unknown value using a rule learned from observed values. NaN means “not a number” and is pandas/NumPy's common missing marker. The median is the middle sorted numeric value; for 100, 200, and 9,000 it is 200, which is less pulled by the outlier than the mean. The mode is the most frequent category; three TCP rows and two UDP rows give TCP. SimpleImputer learns such a statistic with fit and inserts it with transform. KNNImputer instead borrows information from similar rows: KNN is read “k nearest neighbors,” where k is the number of nearby rows consulted. For an intuitive two-feature example, (2,2) is closer to (3,2) than to (10,10). Neighbor distances depend on feature scale and missingness, so KNN is not automatically more truthful.

The page first replaces listed bad strings with NaN, coerces numeric columns, validates IPs, then demonstrates median and mode imputers. It subsequently shows KNNImputer on the already simply imputed numeric columns. **At that point KNN has no missing numeric values to fill**, so it is not a meaningful second repair step. The study notebook runs KNN on a separate pre-imputation copy to make the comparison honest. HTB also includes threat_level among numeric imputation columns. That can create a **fabricated answer label**; the notebook reproduces it in an explicitly labeled course-demonstration branch that is **never used for training**. A second feature-only branch leaves unknown target labels unknown and reports how many supervised rows would remain.

In the course-style branch, median imputation turns the four unknown threat labels into four invented numeric labels. In the feature-only branch, all four remain unknown, leaving **96 originally labeled rows** as possible supervised candidates before any further split or model preparation.

Replacing an unknown source IP with 0.0.0.0 supplies a missing-value sentinel, **not the original source host**. Clipping an out-of-range port to 65535 creates a plausible but invented port. These are the page's illustrative domain rules, not evidence-preserving defaults for a real intrusion detector. In a real pipeline, keep the raw value and an invalid/missing indicator, decide repair rules with domain owners, and fit any learned imputer **only on training data after the split**. This section has no training split yet, so all imputation here is descriptive demonstration, not a validated deployment pipeline.
